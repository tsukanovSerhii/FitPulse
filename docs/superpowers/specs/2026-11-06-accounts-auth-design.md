# Етап 2: акаунти й JWT

Дата: 2026-11-06. Статус: на погодженні. Попередній етап: [фундамент](./2026-11-06-backend-foundation-design.md).

## Мета

Справжні акаунти на сервері замість локальних у браузері. Користувач реєструється й входить як і раніше, а наявні локальні акаунти разом з усіма даними на пристрої непомітно переходять на сервер. Застосунок і далі відкривається без мережі. Адміністратори входять в адмін-панель зі своїми ролями.

Що вирішено разом із власником проєкту:

| Питання | Рішення |
|---|---|
| Обсяг | Сервер і фронт разом: реєстрація, вхід, refresh, вихід, скидання пароля, вхід адмінів; фронт переходить на серверні акаунти |
| Листи | Resend у продакшені, Mailpit у `docker compose` для розробки; один інтерфейс `Mailer` |
| Локальні акаунти | Прив'язуються автоматично під час входу, без додаткових кроків для користувача |
| Токени | Access JWT на 15 хвилин у пам'яті, refresh-токен у cookie `httpOnly` з ротацією, сесії в Postgres, ліміти й відкликання в Redis |

Не входить: підтвердження email, вхід через Google, видалення акаунта, синхронізація даних тренувань (етап 3), керування користувачами в адмінці (етап 4). Аватар лишається на пристрої до етапу зі сховищем файлів.

## API застосунку (`backend`)

| Метод і шлях | Тіло | Відповідь |
|---|---|---|
| `POST /api/auth/register` | `{ name, email, password, remember }` | 201 `{ accessToken, user }` і cookie |
| `POST /api/auth/login` | `{ email, password, remember }` | 200 `{ accessToken, user }` і cookie |
| `POST /api/auth/refresh` | — (cookie) | 200 `{ accessToken, user }` і нова cookie |
| `POST /api/auth/logout` | — (cookie) | 204, сесію відкликано, cookie стерто |
| `POST /api/auth/password/forgot` | `{ email }` | завжди 204 |
| `POST /api/auth/password/reset` | `{ token, password }` | 204, усі сесії користувача відкликано |
| `GET /api/me` | — | 200 `user` |
| `PATCH /api/me` | `{ name?, email?, currentPassword? }` | 200 `user`; зміна email вимагає `currentPassword` |

`user` = `{ id, name, email, plan: 'free' | 'pro', createdAt }`. Схеми запитів і відповідей лежать у `packages/contracts` і спільні з фронтом (ім'я 2–60 символів, пароль від 8 символів, як у поточних формах).

Помилки (у спільній формі `{ error: { code, message } }`, повідомлення українською):

| Ситуація | Статус і код |
|---|---|
| Email уже зайнятий | 409 `EMAIL_TAKEN` «Акаунт з таким email уже існує» |
| Невірний email або пароль (зокрема неіснуючий email) | 401 `INVALID_CREDENTIALS` «Невірний email або пароль» |
| Акаунт заблоковано (`blockedAt`) | 403 `ACCOUNT_BLOCKED` |
| Немає, протермінований чи відкликаний access-токен | 401 `UNAUTHORIZED` |
| Refresh-токен невідомий, протермінований чи використаний повторно | 401 `SESSION_EXPIRED` |
| Refresh-токен щойно замінила інша вкладка | 409 `REFRESH_RETRY` |
| Посилання для скидання пароля недійсне | 400 `RESET_TOKEN_INVALID` |
| Забагато спроб | 429 `RATE_LIMITED` з `Retry-After` |

## API адмінки (`backend-AdminPanel`)

`POST /api/auth/login`, `POST /api/auth/refresh`, `POST /api/auth/logout`, `GET /api/me` працюють так само, але з таблицями `AdminUser` і `AdminSession`. `user` містить ще `role: 'manager' | 'admin'`. Реєстрації й скидання пароля немає: першого адміна створює сід, решту — адмін на етапі 4. Відключений адмін (`disabledAt`) отримує 403 `ACCOUNT_DISABLED`.

## Токени й сесії

- **Access JWT** (HS256, бібліотека `jose`): `sub` (id акаунта), `sid` (id сесії), в адмінці також `role`; живе 15 хвилин. Підписується `JWT_SECRET` або `ADMIN_JWT_SECRET`. Перевірка не звертається до бази. Redis тримає множину відкликаних `sid` з TTL 15 хвилин, щоб вихід і скидання пароля діяли одразу.
- **Refresh-токен**: 32 випадкові байти (base64url) у cookie `fp_refresh` (в адмінці `fp_admin_refresh`), `httpOnly`, `SameSite=Lax`, `Path=/api/auth`, `Secure` у продакшені. У базі лише SHA-256 токена.
- **Тривалість**: «Запам'ятати мене» — cookie й сесія на 30 днів; без нього cookie без `Max-Age` (до закриття браузера), сесія на сервері 12 годин; адмінська сесія — 8 годин без продовження.
- **Ротація**: кожен refresh видає новий токен, а попередній хеш зберігається в сесії разом із часом заміни. Попередній токен протягом 10 секунд після заміни дає 409 `REFRESH_RETRY`, бо так буває, коли дві вкладки оновлюють токен одночасно. Пізніше він означає крадіжку, і сесію відкликано (401).
- **CSRF**: cookie `SameSite=Lax`, ендпоінти приймають лише `application/json`, тож чужий сайт не може надіслати такий запит без CORS.
- **Проксі**: обидва бекенди вмикають `trustProxy`, щоб брати IP клієнта для лімітів з `X-Forwarded-For`, а nginx передає `X-Forwarded-Proto` з `$http_x_forwarded_proto`, бо TLS на Render завершується до nginx.

## Ліміти частоти (Redis, фіксоване вікно)

| Дія | Ліміт |
|---|---|
| Вхід | 5 на хвилину на IP + email і 20 на хвилину на IP |
| Реєстрація | 5 на годину на IP |
| Скидання пароля (запит листа) | 3 на годину на email і 10 на годину на IP |
| Refresh | 60 на хвилину на IP |

Якщо Redis недоступний, запит пропускається без ліміту й пишеться попередження в лог: вхід важливіший за захист від перебору на кілька хвилин.

## База

Друга міграція:

- `User`: нові поля `name` (text) і `plan` (enum `Plan { FREE PRO }`, за замовчуванням `FREE`).
- `Session` і `AdminSession`: `refreshTokenHash` стає унікальним; нові поля `previousTokenHash`, `rotatedAt`, `remember` (bool).
- Нова таблиця `PasswordResetToken`: `id`, `userId` → `User` (каскад), `tokenHash` (унікальний, SHA-256), `expiresAt` (1 година), `usedAt`, `createdAt`. Новий запит скидання робить попередні невикористані посилання недійсними.

## Листи

```ts
interface Mailer {
  send(message: { to: string; subject: string; text: string; html: string }): Promise<void>
}
```

| `MAIL_PROVIDER` | Реалізація | Де |
|---|---|---|
| `resend` | HTTP-запит до `https://api.resend.com/emails` з `RESEND_API_KEY` | продакшен |
| `smtp` | Nodemailer на `SMTP_URL` | Mailpit у `docker compose` (SMTP `:1025`, скринька `http://localhost:8025`) |
| `log` | пише лист у лог | тести й запуск без пошти |

`MAIL_FROM` — адреса відправника, `APP_URL` — публічна адреса застосунку для посилання `APP_URL/reset-password?token=…`. Лист українською: тема «Відновлення пароля FitPulse», посилання й примітка, що воно діє годину. Якщо лист не вдалося надіслати, помилка пишеться в лог, а відповідь лишається 204, щоб не підказувати, чи існує email.

## Спільний код бекендів

Логіка автентифікації однакова для застосунку й адмінки, тому вона лежить у `packages/server-core`, а бекенди лише під'єднують свої таблиці:

- `passwords`: `hashPassword`, `verifyPassword` (argon2id); переноситься з `packages/db`, сід використовує його.
- `tokens`: видача й перевірка access JWT, генерація й хешування refresh-токенів.
- `rateLimit(redis, key, limit, windowSeconds)`.
- `authenticate`: Fastify-хук, що перевіряє `Authorization: Bearer` і відкликані `sid`, і кладе `request.auth = { accountId, sessionId, role? }`.
- `createSessionStore(...)`: створення, ротація й відкликання сесій поверх переданих функцій доступу до таблиці, щоб одна логіка працювала з `Session` і `AdminSession`.
- Плагін `@fastify/cookie`.

## Фронт застосунку

**HTTP-клієнт** (`shared/api/http.ts`): тримає access-токен у пам'яті, додає його в `Authorization`, на 401 `UNAUTHORIZED` один раз викликає refresh і повторює запит. Одночасні refresh об'єднуються в один, а між вкладками їх розводить `navigator.locks`. На 409 `REFRESH_RETRY` refresh повторюється один раз.

**`features/auth/api/authApi`** переходить із `localStorage` на HTTP. Публічні дії слайса лишаються ті самі (`registerUser`, `loginUser`, `logout`, `syncAccount`, `setAvatar`), додаються `restoreSession`, `requestPasswordReset`, `resetPassword`.

**Запуск і офлайн.** Останній відомий користувач кешується на пристрої (`fitpulse_auth_user_v1` у `localStorage` для «Запам'ятати мене», інакше в `sessionStorage`). Під час старту застосунок одразу показує цього користувача, а у фоні викликає refresh:
- успіх — оновлює дані користувача й токен;
- 401 `SESSION_EXPIRED` — вихід на сторінку входу;
- немає мережі — лишається з кешованим користувачем, тренування працюють як і зараз, повторна спроба після події `online`.

**Прив'язка локальних акаунтів.** Старі акаунти лишаються в `fitpulse_accounts_v1`, доки їх не прив'яжуть.
1. Вхід: спершу запит на сервер. Якщо сервер відповів `INVALID_CREDENTIALS`, а на пристрої є локальний акаунт із цим email і пароль збігається з його PBKDF2-хешем, застосунок реєструє серверний акаунт з тим самим ім'ям, email і паролем.
2. Після будь-якого успішного входу чи реєстрації дані з ключів `назва:<локальний id>` локального акаунта з тим самим email переносяться на `назва:<серверний id>`, якщо під серверним id цього ключа ще немає. Потім локальний акаунт видаляється зі списку.
3. Якщо реєстрація на кроці 1 повертає `EMAIL_TAKEN` (акаунт уже створено з іншого пристрою з іншим паролем), користувач бачить «Невірний email або пароль», а локальні дані чекають на вхід із серверним паролем.

Аватар переїжджає з облікового запису в дані користувача на пристрої (ключ `fitpulse_avatar_v1` серед `USER_KEYS`) і переноситься разом з іншими даними.

**Нові сторінки**: `/forgot-password` (форма email, після відправки — «Якщо акаунт існує, ми надіслали лист») і `/reset-password?token=…` (новий пароль двічі, після успіху — на вхід). На сторінці входу з'являється посилання «Забули пароль?». У профілі зміна email показує поле поточного пароля.

**Повідомлення** на формах — ті самі, що зараз, плюс «Забагато спроб. Спробуйте за N хв» для 429 і «Немає з'єднання з сервером» для мережевих помилок під час входу й реєстрації.

## Адмін-панель

Сторінка входу (email, пароль) → після входу шапка «Ви увійшли як `email` (адміністратор | менеджер)» і кнопка «Вийти». Під час завантаження панель відновлює сесію через refresh. Решта інтерфейсу з'явиться на етапі 4.

## Docker, Render, CI

- `docker compose`: сервіс `mailpit` (`axllent/mailpit`, порти 8025 і 1025); `api` отримує `MAIL_PROVIDER=smtp`, `SMTP_URL=smtp://mailpit:1025`, `APP_URL=http://localhost:5173`.
- `render.yaml`: `fitpulse-api` отримує `MAIL_PROVIDER=resend`, `RESEND_API_KEY` і `MAIL_FROM` (`sync: false`), `APP_URL` (`sync: false`).
- `vite preview` проксіює `/api` так само, як dev-сервер, щоб e2e-тести працювали зі справжнім API.
- CI `e2e`: Postgres і Redis як service-контейнери, міграції, запуск зібраного `backend` з `MAIL_PROVIDER=log`, далі Playwright як зараз.

## Тести

**Бекенд, інтеграційні (Postgres + Redis):**
- реєстрація створює акаунт і сесію, повертає токен і cookie з потрібними атрибутами; повторний email у будь-якому регістрі — 409;
- вхід із правильним паролем — 200; з неправильним і з неіснуючим email — однаковий 401; заблокований — 403;
- refresh міняє cookie; старий токен одразу після заміни — 409; через 10 секунд — 401 і сесія відкликана;
- вихід: refresh після нього — 401, access-токен цієї сесії — 401 одразу;
- шоста спроба входу за хвилину — 429 з `Retry-After`;
- скидання: лист із посиланням потрапляє в тестовий `Mailer`; новий пароль працює, старий ні, усі сесії відкликано; посилання вдруге й протерміноване — 400; запит для неіснуючого email — 204 без листа;
- `PATCH /api/me`: ім'я змінюється; email без пароля — 400, з неправильним — 401;
- адмінка: вхід адміна й менеджера з роллю в токені; відключений — 403; access-токен застосунку не приймається адмінкою й навпаки.

**Unit:** перевірка й протермінування JWT, хешування токенів, ліміт без Redis пропускає запит.

**Фронт (Vitest):** HTTP-клієнт оновлює токен один раз на кілька паралельних 401; прив'язка переносить ключі й не перезаписує наявні; запуск без мережі лишає кешованого користувача; 401 під час запуску виходить.

**E2E (Playwright зі справжнім API):** реєстрація й вхід як зараз; сторінка «Забули пароль?» показує підтвердження після відправки (повний шлях листа перевіряють інтеграційні тести бекенду); локальний акаунт, створений у `localStorage` до входу, після входу бачить свою історію тренувань.
