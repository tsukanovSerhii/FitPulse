# Етап 4a: адмін-панель (користувачі, статистика, співробітники)

Дата: 2026-11-08. Статус: погоджено в чаті (продовження обсягу A + C етапу 4). Керування вправами й програмами (B) — окремий етап 4b: каталог зараз у коді й з нього пререндеряться 135 сторінок для пошуковиків, тож перенесення в базу потребує власного рішення.

## Ролі

| Дія | Менеджер | Адмін |
|---|---|---|
| Статистика, список і картка користувача | так | так |
| Заблокувати / розблокувати | так | так |
| Змінити тариф (free / pro) | ні | так |
| Видалити користувача з усіма даними | ні | так |
| Список співробітників, створити, вимкнути, змінити роль | ні | так |
| Журнал дій | так (свої) | так (усі) |

Перевірка ролі — на сервері (`requireRole('admin')` поверх `authenticate`); роль береться з бази на кожен запит, а не лише з токена, тож пониження діє одразу. Адмін не може вимкнути або понизити сам себе.

## API (`backend-AdminPanel`, усе під `/api`, потрібен вхід)

| Метод і шлях | Роль | Що робить |
|---|---|---|
| `GET /stats` | будь-яка | `{ users, newUsers7d, newUsers30d, activeUsers7d, workouts, workouts7d, proUsers, blockedUsers }` |
| `GET /users?query=&status=&page=` | будь-яка | пошук за email або ім'ям (без урахування регістру), статус `all/active/blocked`, 20 на сторінку, нові спершу |
| `GET /users/:id` | будь-яка | акаунт, кількість тренувань і вимірів, остання синхронізація, активні сесії |
| `POST /users/:id/block` | будь-яка | `blockedAt = now`, усі сесії відкликано (і в Redis, тож access-токени зупиняються одразу) |
| `POST /users/:id/unblock` | будь-яка | `blockedAt = null` |
| `PATCH /users/:id` `{ plan }` | адмін | тариф `free` або `pro` |
| `DELETE /users/:id` | адмін | видаляє акаунт і все пов'язане (каскад) |
| `GET /staff` | адмін | співробітники |
| `POST /staff` `{ email, password, role }` | адмін | новий співробітник (пароль від 12 символів) |
| `PATCH /staff/:id` `{ role?, disabled? }` | адмін | роль або вимкнення; вимкнення відкликає сесії |
| `GET /audit?page=` | будь-яка | журнал: менеджер бачить свої дії, адмін — усі |

Застосунок теж має знати про блокування: `POST /api/sync` перевіряє, що акаунт не заблоковано (403 `ACCOUNT_BLOCKED`).

## Журнал дій

Таблиця `admin_audit_log`: `id`, `admin_id` → `admin_users` (null при видаленні адміна), `action` (`user.block`, `user.unblock`, `user.plan`, `user.delete`, `staff.create`, `staff.update`), `target_id`, `details` (JSONB), `created_at`. Кожна змінна дія пишеться в одній транзакції з самою зміною.

## Інтерфейс (`frontend-AdminPanel`)

- React Router: `/` статистика, `/users` пошук і список, `/users/:id` картка з діями, `/staff` (лише адмін), `/audit`.
- Шапка: розділи, «Ви увійшли як … (роль)», «Вийти». Пункти й кнопки, недоступні ролі, не показуються.
- Небезпечні дії (блокування, видалення) просять підтвердження; видалення — ввести email користувача.
- Клієнт додає access-токен і на 401 один раз оновлює сесію.

## Тести

- Інтеграційні (адмін-API): статистика рахує правильно; пошук за частиною email і ім'я, сторінки; блокування відкликає сесії й зупиняє access-токен застосунку; менеджер отримує 403 на тариф, видалення й співробітників; адмін не може вимкнути себе; кожна зміна пише журнал; менеджер бачить лише свої записи.
- API застосунку: заблокований акаунт отримує 403 на `/api/sync`.
- Інтерфейс: пошук і перехід у картку; кнопок адміна немає в менеджера; блокування з підтвердженням.
