# Етап 3: синхронізація даних між пристроями

Дата: 2026-11-07. Статус: погоджено в чаті.

## Мета

Дані акаунта однакові на всіх пристроях, а без мережі застосунок працює як зараз: зміни чекають на пристрої й відправляються, коли з'являється зв'язок. Модулі `api/` фіч не змінюються; синхронізацію робить окремий шар.

## Що синхронізується

| `kind` | Ключ на пристрої | Одиниця | `id` запису |
|---|---|---|---|
| `workout` | `fitpulse_history_v1` | кожне тренування | `id` тренування |
| `body` | `fitpulse_body_log_v1` | кожен вимір | `id` виміру |
| `plan` | `fitpulse_plans_v1` | кожна програма | `id` програми |
| `exercise` | `fitpulse_exercises_v1` | кожна власна вправа | `id` вправи |
| `setting` | профіль, ціль тижня, обладнання, суглоби, активна програма, обране, нотатки | значення ключа цілком | назва ключа (`fitpulse_profile_v1` …) |

Не синхронізуються: рекорди (рахуються з журналу), активне тренування, аватар, тема.

## Сервер

Таблиця `sync_records`: `user_id` → `users` (каскад), `kind`, `record_id`, `data` (JSONB, `null` для видаленого), `updated_at`, `deleted_at`, `seq` (BIGSERIAL, унікальний). Первинний ключ `(user_id, kind, record_id)`, індекс `(user_id, seq)`.

`POST /api/sync` (потрібен access-токен):

```
→ { cursor: string, changes: [{ kind, id, data: unknown | null, updatedAt }] }
← { applied: number, cursor: string, hasMore: boolean, changes: [{ kind, id, data | null, updatedAt }] }
```

1. Кожна зміна пишеться одним `INSERT … ON CONFLICT DO UPDATE … WHERE sync_records.updated_at < EXCLUDED.updated_at`, і `seq` отримує нове значення. Застаріла зміна не пишеться.
2. `updatedAt`, що випереджає час сервера більше ніж на 5 хвилин, замінюється часом сервера.
3. Відповідь — записи користувача з `seq > cursor` за зростанням `seq`, до 500 штук, без тих, що записав цей самий запит. `cursor` — останній віддане `seq` (рядком), `hasMore` — чи лишилися ще.
4. Межі: `kind` з таблиці вище; `id` до 100 символів; до 500 змін за запит; запис до 64 КБ JSON; 30 запитів на хвилину на користувача. Порушення — 400 `VALIDATION_ERROR` або 429.

## Пристрій (`features/sync`)

- Стан на пристрої в ключі `fitpulse_sync_v1:<userId>`: `{ cursor, hashes: { "<kind>:<id>": "<hash>" } }`. Хеш — FNV-1a від JSON запису.
- **Обмін** (`syncNow`):
  1. Зібрати поточні записи з ключів таблиці; ті, що змінились проти `hashes`, нові та зниклі стають змінами (`updatedAt` = зараз, зниклі — `data: null`). Налаштування, якого ключа немає на пристрої, не надсилається.
  2. `POST /api/sync`; поки `hasMore`, повторювати з порожніми змінами.
  3. Отримані записи записати в сховище (вставка або заміна за `id`, видалення для `null`; налаштування — значення ключа), оновити `hashes` і `cursor`. Якщо прийшли тренування, ключ рекордів видаляється, щоб вони перерахувались із журналу.
  4. Якщо щось прийшло — заново завантажити слайси: вправи, програми, прогрес, профіль, тіло.
- **Коли:** після входу й старту; через 2 с після будь-якої успішної дії, що змінює дані (debounce); на подію `online`; раз на 60 с, поки вкладка видима. Один обмін за раз, між вкладками — `navigator.locks` (`fitpulse-sync`).
- **Перший вхід на пристрої** (`cursor` = `"0"`, `hashes` порожні): локальні записи надсилаються як нові, серверні приходять — дані зливаються, нічого не видаляється. Конфлікт за однаковим `id` вирішує новіший `updatedAt`.
- **Без мережі або 5xx**: зміни лишаються невідправленими, наступна спроба за розкладом; 401 спершу оновлює токен (наявний HTTP-клієнт).
- **Стан** у профілі: «Синхронізовано щойно / о 14:05», «Очікує мережі», «Помилка синхронізації».

## Тести

- Сервер (інтеграційні): новіша зміна перемагає, старіша ні; видалення доходить до іншого пристрою; курсор віддає лише нові записи; не видно чужих даних; час з майбутнього обрізається; поділ на сторінки; межі.
- Пристрій (unit): диф дає нові, змінені й видалені записи і не дає незмінних; застосування записує в сховище й видаляє; рекорди скидаються після тренувань; перший вхід зливає; без мережі зміни повторюються наступного разу.
- E2E: тренування, записане в одному браузерному контексті, з'являється в другому контексті того самого акаунта.
