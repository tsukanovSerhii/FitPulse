# Sync (Stage 3) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Account data syncs between devices through `POST /api/sync` while the app keeps working offline.

**Architecture:** One `sync_records` table with JSONB rows and a per-row `seq` cursor; the API upserts newer rows and pages changes since the cursor. On the device, `features/sync` diffs the per-user storage keys against stored hashes, exchanges changes, writes received rows back to storage and reloads the slices.

**Spec:** `docs/superpowers/specs/2026-11-07-sync-design.md`

## Global Constraints

- Kinds: `workout | body | plan | exercise | setting`; ids ≤ 100 chars; ≤ 500 changes per request; row JSON ≤ 64 KB; page 500; 30 requests/min/user.
- Cursor is a decimal string of `seq`; `"0"` means nothing received yet.
- Future `updatedAt` > server now + 5 min is clamped to now.
- Device state key `fitpulse_sync_v1:<userId>`; FNV-1a 32-bit hex of `JSON.stringify(value)`.
- Setting ids are the storage key names: profile, weekly goal, equipment, limits, active plan, favorites, notes.

## Review Focus

1. Two devices record different workouts offline → both survive (distinct ids).
2. A setting changed on two devices → the newer one wins on both after a round.
3. A device with a wrong clock far in the future cannot freeze a record — clamped.
4. Hundreds of records on first sign-in → pages until `hasMore` is false.
5. Offline sync attempt → no data lost, retried later.
